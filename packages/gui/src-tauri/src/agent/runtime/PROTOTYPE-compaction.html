When to compact, and what survives

The question. The same session runs through two ways of managing context side by side. Does compacting at a calm moment, holding it while work is open, and merging the summary bit by bit beat compacting only when the window is nearly full and rewriting the summary each time? Press buttons and watch each side decide.

Today (how the app behaves now): compacts only when the window is within the reserve of full, at any moment between tool calls; the summary is rewritten from the old summary plus the old messages. Proposed (from the brainstorm): compacts at a breakpoint (tests pass, commit, task done, plan change) once past 50%, clears old tool output first, holds while work is open (failing tests, files mid-edit, a tool call waiting), forces it at 85%; the summary is merged bit by bit and the file list comes from the tool log.

Assumptions, to check against real runs: token sizes are typical, not measured. “Rewritten” summaries are modelled as keeping only the headline of anything from an earlier summary and dropping it after a second rewrite, unless it is the original request. That is the drift the Factory evaluation describes; the real rate is what this should be calibrated against.

Both sides get exactly the same events.
